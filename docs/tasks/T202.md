# T202 — Secret settings as `SecretStr`

**Task**: Hold secret settings as `SecretStr` and unwrap them only at their point of use in
`backend/app/config.py`.

## The change

Four settings changed type from `str` to pydantic's `SecretStr`:

| Setting | Why it is secret |
|---|---|
| `reddit_client_secret` | Reddit API credential |
| `groq_api_key` | Model provider credential |
| `database_url` | The connection string contains the database password |
| `auth_password_hash` | Not a password, but a hash someone could attack offline |

`SecretStr` is a wrapper that prints as `**********`. The value is still there, but only an explicit
call gets it out:

```python
settings.groq_api_key                     # SecretStr('**********')
settings.groq_api_key.get_secret_value()  # the real key
```

So `print(settings)`, `logger.debug(settings)`, or an f-string containing it no longer leaks
anything. That makes the safe outcome the default instead of something every future log line has
to remember.

`reddit_client_id` and `auth_username` stayed plain strings. They identify things but grant nothing
on their own.

## Where secrets are unwrapped

Each place that genuinely needs a value now asks for it explicitly:

- `app/reddit/client.py` — `settings.reddit_client_secret.get_secret_value()` when building PRAW's
  client.
- `app/common/database.py` — `settings.database_url.get_secret_value()` when creating the engine.
- `app/users/auth_service.py` — `settings.auth_password_hash.get_secret_value()` in `authenticate`.

A useful side effect is that `grep get_secret_value` now lists every place a secret leaves its
wrapper. Before, a secret was indistinguishable from any other string.

## One trap: the default value

The password hash defaults to empty, because an unconfigured credential must lock everyone out (see
T020). The obvious way to write that is wrong:

```python
auth_password_hash: SecretStr = Field(default="")          # stays a plain str!
auth_password_hash: SecretStr = Field(default=SecretStr(""))  # correct
```

Pydantic does **not** validate default values, so `default=""` leaves a bare `str` in a field
declared as `SecretStr`. On a fresh checkout, `authenticate` would then crash calling
`.get_secret_value()` on a string, instead of failing closed. The third test in T201 exists to catch
exactly this.

## What changed in the existing tests

Tests that configure a credential monkeypatch `settings.auth_password_hash`. They now patch a
`SecretStr(...)` instead of a bare string, so the code under test sees the same type it sees in
production. Five lines across `test_auth_service.py` and `test_auth_routes.py`.

## What this does not cover

`backend/alembic/env.py` still reads `DATABASE_URL` with `os.getenv` rather than through
`app/config.py`. That bypasses the "only `config.py` reads secrets" rule, but it doesn't log the
value, so it's outside this task. It's recorded as a follow-up rather than fixed silently here.
