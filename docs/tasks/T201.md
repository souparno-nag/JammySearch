# T201 — Tests that secrets stay out of logs and printed settings

**Task**: Write failing tests asserting secrets never appear in settings output, sign-in logs, or
session logs in `backend/tests/unit/test_secret_redaction.py` and
`backend/tests/integration/test_auth_logging.py`.

## Why this task exists

FR-079 says secrets must "never appear in responses, logs, or anything the client can read". When
`/speckit-analyze` looked for the tasks enforcing that, it found tests for hashing passwords and
expiring sessions (T019) and nothing at all about logs. That was finding H3.

Reading the code showed the log statements themselves were fine. The sign-in route logs only
`"sign-in refused"`, with no username, password, or reason attached. The real gap was somewhere less
obvious, in `backend/app/config.py`:

```python
reddit_client_secret: str = Field(alias="REDDIT_CLIENT_SECRET")
groq_api_key: str = Field(alias="GROQ_API_KEY")
```

Every secret was a plain `str`. A pydantic model prints all of its fields, so this:

```python
logger.debug("loaded settings: %s", settings)
```

would have written the Reddit secret, the Groq key, the database password, and the password hash
into the log in full. Nobody had written that line yet. But it is exactly the line someone writes
at 1 a.m. while chasing a configuration bug, and nothing would have stopped it.

## What the tests check

**`tests/unit/test_secret_redaction.py`**, about the settings object itself:

- Rendering it four ways (`repr`, `str`, `model_dump_json()`, `model_dump()`) never shows any secret.
  Each secret is a recognisable sentinel string such as `"groq-key-sentinel"`, so the test can search
  the output for it. For the database URL the sentinel is just the password inside it, because
  that is the part that matters.
- Each secret can still be read through `.get_secret_value()`. Redaction that made the key unusable
  would be no fix.
- An unconfigured password hash defaults to an *empty secret*, not to a plain empty string. This
  matters for the fail-closed check in `auth_service.py` (see T202).

`Settings` is built with `_env_file=None`, so these tests read neither your local `.env` nor whatever
happens to be in the environment.

**`tests/integration/test_auth_logging.py`**, about the sign-in path:

- A refused sign-in logs neither the attempted password nor the stored hash.
- A successful sign-in logs neither the password nor the session token it just issued.

These capture *every* log record from *every* logger at DEBUG level, and check each record's
message, arguments, and `extra` fields. A secret passed as structured context leaks just as surely as
one in the message text. They are integration tests because the request passes through the router,
the rate limiter, and the error middleware, and any of the three could be where a future log line
appears (Constitution IV requires integration tests for anything that crosses module boundaries).

## Did they fail first?

Yes. That is what "write failing tests" means, and Constitution IV requires it. Before T202:

```
assert 'reddit-secret-sentinel' not in "Settings(re...'127.0.0.1')"
```

That failure is the leak itself, caught by a test instead of found in a log file. The log tests
failed too, but only because they configure the credential as a `SecretStr`, which the code didn't
understand yet. They are guards on code that was already clean, so they exist to keep it that way.

## Note

The two log tests passing today does not mean they are redundant. Their job is to fail the day
someone adds `logger.info("sign-in attempt", extra={"body": credentials})`.
